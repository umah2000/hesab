# قواعد ثبت اسناد حسابداری و گردش موجودی

## ۱. اصول
1. هر رویداد عملیاتی قطعی ← دقیقاً یک سند حسابداری (یا هیچ، اگر اثر مالی ندارد) **در همان تراکنش دیتابیس**.
2. حساب‌ها از جدول `posting_rule` خوانده می‌شوند، نه از کد. کد فقط «نقش ردیف» (line role) و مبلغ را تعیین می‌کند.
3. سند خودکار مستقیماً با وضعیت «قطعی» یا «موقت» (تنظیم سازمان) ثبت می‌شود و `source_type`/`source_id` دارد.
4. برگشت = سند معکوس با پیوند به سند اصلی؛ هرگز ویرایش سند اصلی.
5. جمع بدهکار = جمع بستانکار، بررسی در service قبل از commit؛ اختلاف ← خطا و rollback کل عملیات.
6. نبود posting rule برای یک نقش ← خطای پیکربندی و عدم ثبت عملیات (نه سند ناقص).

## ۲. نقش‌های ردیف و نگاشت پیش‌فرض

### فروش قطعی (`sales.invoice.finalized`)
| نقش | سمت | مبلغ | حساب پیش‌فرض |
|---|---|---|---|
| `cash` | بد | سهم نقد | صندوق شیفت |
| `card` | بد | سهم کارت | حساب واسط کارت‌خوان / بانک متصل به ترمینال |
| `receivable` | بد | سهم نسیه | حساب‌های دریافتنی (تفصیلی: مشتری) |
| `revenue` | بس | جمع قبل از تخفیف | فروش کالا |
| `discount` | بد | تخفیف | تخفیفات فروش |
| `vat_payable` | بس | مالیات و عوارض | مالیات بر ارزش افزوده پرداختنی |
| `cogs` | بد | بهای تمام‌شده (از گردش انبار) | بهای تمام‌شده کالای فروش‌رفته |
| `inventory` | بس | همان | موجودی کالا |

### برگشت از فروش (`sales.return.finalized`)
معکوس فروش، با حساب «برگشت از فروش» به‌جای `revenue`؛ بهای تمام‌شده با **همان میانگین ثبت‌شده در فروش اصلی** برمی‌گردد.

### سایر رویدادها
| رویداد | بدهکار | بستانکار |
|---|---|---|
| رسید خرید | موجودی کالا، مالیات خرید | حساب‌های پرداختنی (تأمین‌کننده) |
| برگشت خرید | پرداختنی | موجودی، مالیات خرید |
| دریافت از مشتری | صندوق/بانک | دریافتنی |
| پرداخت به تأمین‌کننده | پرداختنی | صندوق/بانک |
| تعدیل کاهشی موجودی | کسری انبار (هزینه) | موجودی |
| تعدیل افزایشی | موجودی | اضافه انبار (درآمد متفرقه) |
| بستن شیفت — کسری | کسری صندوق | صندوق |
| بستن شیفت — اضافه | صندوق | اضافه صندوق |
| تسویه کارت‌خوان | بانک | حساب واسط کارت‌خوان |

## ۳. گردش موجودی
- فروش قطعی ← سند انبار نوع `issue` از انبار صندوق؛ هر ردیف ← `stock_ledger` با `avg_cost` جاری؛ `stock_balance` در همان تراکنش.
- قفل ردیف `stock_balance` (`UPDLOCK, ROWLOCK`) به ترتیب ثابت `item_id` برای جلوگیری از deadlock بین صندوق‌ها.
- سیاست موجودی منفی: `deny` (خطا و توقف فاکتور) · `warn` (اجازه + هشدار + گزارش) · `allow`. پیش‌فرض سوپرمارکت: `warn` (تأییدشده Q5).
- کالای خدماتی گردش انبار ندارد.

## ۴. ترتیب عملیات در «قطعی کردن فاکتور»
```
unit_of_work:
  1. بررسی Idempotency-Key
  2. قفل و اعتبارسنجی فاکتور (draft/held، شیفت باز، مجوز)
  3. محاسبه نهایی قیمت/تخفیف/پروموشن/مالیات در سرور (عدد Frontend معتبر نیست)
  4. بررسی پرداخت‌ها: جمع = grand_total؛ کارت فقط با terminal_transaction در وضعیت Approved (یا ثبت دستی مجاز در پایلوت)
  5. سند انبار issue + ledger + balance
  6. ساخت سند حسابداری از posting rules + بررسی توازن
  7. اختصاص شماره قطعی (number_sequence)
  8. وضعیت final + ممیزی + ذخیره پاسخ idempotency
commit (هر خطا ← rollback همه)
```
