# ADR-0019: HTTPS با پراکسی معکوس و سرآیندهای امنیتی

**وضعیت:** پذیرفته · ۱۴۰۵/۰۷/۲۷ (فاز ۱۰)

## زمینه
- پایلوت روی HTTP در شبکه‌ی داخلی جدا اجرا شد؛ این یک ریسک موقت پذیرفته‌شده بود (لاگ فاز ۴).
- اپ ویزیتور در نسخه‌ی انتشار فقط به HTTPS وصل می‌شود (ADR-0018، Q21).
- waitress (سرور ویندوزی برنامه) TLS ندارد.
- فروشگاه معمولاً دامنه و گواهی عمومی ندارد، و صندوق‌ها و Device Agent باید به گواهی اعتماد کنند.

## تصمیم
1. **TLS در Caddy، روی همان سرور.**
   - Caddy یک فایل اجرایی ویندوزی است و گواهی را خودکار صادر و تمدید می‌کند.
   - **شبکه‌ی فروشگاه:** `tls internal`، یعنی CA محلی Caddy. ریشه‌ی آن یک بار در مخزن Root ویندوز صندوق‌ها نصب می‌شود. مرورگر و Agent (Python روی ویندوز) به همین مخزن اعتماد می‌کنند.
   - **اینترنت (اختیاری، Q21):** دامنه‌ی عمومی با Let's Encrypt. فقط مسیرهای اپ ویزیتور عبور داده می‌شوند.
2. **برنامه فقط روی 127.0.0.1** و `NEXTCAM_TRUSTED_PROXY=127.0.0.1`.
   - waitress آدرس کاربر و `https` را فقط از `X-Forwarded-*` همان پراکسی می‌پذیرد و این سرآیندها را از دیگران پاک می‌کند.
   - در نتیجه قفل ورود، محدودیت تلاش و رویدادنگار، آدرس واقعی کاربر را می‌بینند.
3. **سرآیندهای امنیتی در خود برنامه** (`after_request`)، نه در پراکسی؛ تا روی HTTP پایلوت و پشت هر پراکسی یکسان باشند:
   - CSP سخت‌گیر (`script-src 'self'`، بدون eval و اسکریپت inline)؛ `style-src` به‌خاطر استایل‌های inline React شامل `'unsafe-inline'` است.
   - `frame-ancestors 'none'`، COOP و CORP.
   - Permissions-Policy.
   - `no-store` روی API.
   - HSTS فقط وقتی `NEXTCAM_COOKIE_SECURE=true` است.
4. **بررسی وابستگی‌ها و تحلیل ایستا در CI** (bandit، pip-audit، npm audit)، در هر PR و هفتگی.

## پیامدها
- یک سرویس بیشتر روی سرور (Caddy) که باید پایش و پشتیبان‌گیری شود. کلید CA محلی آن حساس است.
- روشن شدن HSTS برگشت آسان به HTTP را تا یک سال برای همان نام می‌بندد.
- گوشی‌ها به CA داخلی اعتماد نمی‌کنند. برای اپ ویزیتور دامنه‌ی عمومی لازم است، یا VPN به‌همراه گواهی عمومی.
- جزئیات نصب: `docs/install/https.md`. ارزیابی: `docs/security/assessment.md`.
