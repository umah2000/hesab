# پروتکل همگام‌سازی و مدیریت تعارض (پیاده‌شده در فاز ۸ — ADR-0017)

## ۱. چه چیزی آفلاین مجاز است
| عملیات | صندوق آفلاین | موبایل آفلاین (فاز ۹) | دلیل |
|---|:-:|:-:|---|
| فروش نقدی | ✓ | — | ادامه‌ی کار فروشگاه |
| فروش کارتی | ✓ با کارت‌خوان جدا و ثبت شماره پیگیری | — | کارت‌خوان متصل از سرور می‌گذرد |
| فروش نسیه | ✗ | — | نیازمند مانده‌ی لحظه‌ای مشتری |
| برگشت از فروش، فاکتور معلق | ✗ | — | نیازمند فاکتور اصلی و سرور |
| تخفیف بالای اختیار صندوق‌دار، هر تأیید سرپرست | ✗ | — | تأیید فقط آنلاین |
| حذف ردیف اسکن‌شده | ✓ بدون تأیید، ممیزی‌شده | — | ADR-0017 §۸ |
| ورود به سیستم | ✗ (فقط نشستی که سرور پذیرفته) | — | هیچ رمزی روی صندوق نیست |
| ثبت سفارش ویزیتور | — | ✓ | سفارش، نه سند مالی |
| سند حسابداری دستی، تعدیل موجودی | ✗ | ✗ | |

## ۲. داده‌ی پایه‌ی محلی (pull)
- **فراخوانی:** `GET /api/v1/sync/agent/snapshot` با توکن دستگاه.
  - پاسخ با `ETag`؛ اگر چیزی تغییر نکرده باشد، `304`.
  - Agent هر دقیقه و پس از هر ارسال می‌پرسد.
- **محتوا:**
  - صندوق و انبار آن
  - شیفت باز با مجوزهای فروش کاربرش
  - تنظیمات (مالیات، شمول مالیات در قیمت، سقف تخفیف، سیاست موجودی منفی، واحد نمایش، منطقه‌ی زمانی، سر و ته فیش)
  - واحدها، کالاهای فعال با موجودی، ضرایب واحد، قیمت فهرست پیش‌فرض
  - بارکدها، قاعده‌های ترازو، پروموشن‌های جاری
  - `number_prefix`
- **اعتبار:** `valid_until` (۲۴ ساعت). پس از آن فروش آفلاین بسته است.

## ۳. عملیات (push)
`POST /api/v1/sync/agent/push` با بدنه‌ی `{"ops": [...]}`، حداکثر ۵۰ عملیات و به ترتیب ایجاد:
```json
{
  "id": "uuid",                       // operation_id = شناسه‌ی فاکتور = Idempotency-Key
  "type": "sale",                     // یا "line_removal"
  "local_time": "2026-10-16T10:15:00+00:00",
  "sale": {
    "id": "uuid", "device_number": "F902BD16-3", "sold_at": "…",
    "cash_register_id": "…", "shift_id": "…", "user_id": "…",
    "snapshot_version": "…", "prices_include_vat": false,
    "lines": [{ "item_id": "…", "unit_id": "…", "qty": "2.000", "unit_price": "110000.0000",
                "price_source": "list", "gross": "…", "promotion_id": null,
                "promotion_discount": "0", "manual_discount": "0",
                "vat_exempt": false, "vat_rate": "10", "tax": "…", "line_total": "…",
                "scanned_barcode": null }],
    "subtotal": "…", "discount_total": "…", "tax_total": "…", "grand_total": "…",
    "payments": [{ "method": "cash", "amount": "…" }, { "method": "card", "amount": "…", "card_reference": "123456" }],
    "cash_tendered": "…", "note": null
  }
}
```
**پاسخ سرور برای هر عملیات:** `{id, status, code, message, invoice_id, number}`.
- `applied`: ثبت شد، با شماره‌ی قطعی.
  - تکرار همان عملیات همان پاسخ را برمی‌گرداند.
  - اگر فروش آنلاین با همان شناسه و مبلغ قبلاً ثبت شده باشد، کد `already_recorded` دارد.
- `rejected`: هرگز قابل اعمال نیست. نمونه‌ها:
  - داده‌ی نامعتبر یا مبالغ ناسازگار
  - صندوق، شیفت یا پیشوند شماره‌ی بیگانه
  - شناسه‌ی تکراری با مبلغ دیگر
- `conflict`: منتظر تصمیم انسانی (§۴).
- `resolved` / `discarded`: نتیجه‌ی تصمیم مدیر، برای ارسال دوباره‌ی همان عملیات.

**قواعد صف:**
- عملیات معیوب صف را متوقف نمی‌کند.
- عملیات فقط پس از پاسخ سرور از صف بیرون می‌رود.
- در خطای شبکه، تلاش دوباره با backoff (۳ تا ۳۰ ثانیه) انجام می‌شود.

Agent در هر poll تعداد فروش‌های ارسال‌نشده را می‌فرستد (`offline_queue`). سرور تا وقتی این عدد صفر نشود، بستن شیفت آن صندوق را نمی‌پذیرد.

## ۴. قواعد تعارض (هرگز Last-Write-Wins)
| وضعیت | رفتار |
|---|---|
| قیمت در سرور تغییر کرده | ثبت با **قیمت فروخته‌شده**؛ اختلاف با قیمت فعلی در `price_difference` |
| موجودی منفی می‌شود | ثبت (کالا رفته است)؛ هشدار موجودی |
| کالا پس از snapshot غیرفعال شده | ثبت |
| کاربر غیرفعال شده یا مجوز پرداخت/تخفیف ندارد | `conflict` (`not_permitted`) |
| شیفت در سرور بسته شده | `conflict` (`shift_closed`)؛ در صورت پذیرش، مغایرت شیفت جداگانه اصلاح می‌شود |
| سال یا دوره‌ی مالی بسته یا قفل | `conflict` (`period_locked` و …)؛ در صورت پذیرش با تاریخ امروز |
| ساعت صندوق (±۵ دقیقه نسبت به شیفت و سرور) | `conflict` (`clock`) |
| تراکنش کارت بدون نتیجه‌ی قطعی | آفلاین کارت‌خوان متصل نداریم؛ فقط شماره پیگیری رسید |
| payload نامعتبر | `rejected`؛ بقیه‌ی صف ادامه می‌یابد |

**حل تعارض** (`sync.resolve`):
- مسیر: «فروش ← فروش‌های آفلاین».
- «ثبت فروش با همین مبالغ» یا «کنار گذاشتن»، همیشه با توضیح.
- هر دو ممیزی می‌شوند (`sync.operation.resolved` / `discarded`).
- عملیات ردشده فقط کنار گذاشته می‌شود.

## ۵. شماره‌گذاری و تاریخ
- **شماره‌ی صندوق:** `<پیشوند دستگاه>-<دنباله>` روی فیش آفلاین، با ارقام لاتین برای جست‌وجو.
- **شماره‌ی قطعی:** هنگام اعمال در سرور گرفته می‌شود (ADR-0005). هر دو روی فاکتور می‌مانند (`device_number`، `sold_at`).
- **تاریخ:** فاکتور و سند حسابداری تاریخ فروش را دارند. سند انبار تاریخ روز همگام‌سازی را دارد.
