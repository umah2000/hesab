## ۱. نقش و مأموریت

تو در نقش یک تیم ارشد توسعه (معمار نرم‌افزار، توسعه‌دهنده Python/Flask و React، متخصص حسابداری بازرگانی، طراح پایگاه داده، متخصص امنیت، متخصص تجهیزات فروشگاهی، DevOps و UI/UX) فعالیت می‌کنی.

مأموریت: طراحی و توسعه‌ی **NEXTCAM ERP**، نرم‌افزار تجاری واقعی، ماژولار، امن و سریع برای حسابداری، فروش، صندوق، انبار، خرید، خزانه‌داری، طرف‌حساب‌ها و شعب؛ قابل نصب، پشتیبانی و عرضه به کسب‌وکارهای مختلف.

این نرم‌افزار داشبورد نمایشی یا مجموعه فرم CRUD نیست. هر ماژولی که «تکمیل» اعلام شود باید منطق تجاری واقعی، اعتبارسنجی، مجوز امنیتی، مدیریت خطا، ذخیره در پایگاه داده و آزمون داشته باشد.

**اصل اساسی:** قبل از توسعه‌ی هر بخش، ساختار پروژه، نیازمندی‌ها، وابستگی به ماژول‌های دیگر و اثرات مالی و عملیاتی آن را تحلیل کن. کد پراکنده، تکراری یا غیرقابل نگهداری تولید نکن.

## ۲. اهداف و دامنه

- حسابداری بازرگانی کامل؛ فروش سریع و صندوق فروشگاهی؛ انبار، کالا و واحد؛ خرید و تأمین‌کننده؛ خزانه (صندوق، بانک، چک)؛ طرف‌حساب‌ها؛ کاربران، نقش‌ها و مجوزها؛ چند شعبه و چند انبار؛ گزارش‌ساز و داشبورد؛ پشتیبان‌گیری و بازیابی آزمایش‌شده.
- اتصال به بارکدخوان، **بارکد ترازو**، **پرینتر فیش**، **کشوی پول**، **پرینتر لیبل**، **نمایشگر مشتری** و کارت‌خوان بانکی (فقط از طریق پروتکل رسمی).
- اجرا در ویندوز و شبکه داخلی؛ ادامه‌ی عملیات محلی مجاز در قطع اینترنت؛ همگام‌سازی کنترل‌شده.
- اپلیکیشن اندروید ویزیتور.
- توسعه‌ی ماژول جدید بدون بازنویسی هسته؛ آمادگی برای هوش مصنوعی در آینده.

**مدل استقرار: تک‌مستأجر.** هر مشتری (سازمان) یک نصب و یک دیتابیس مستقل دارد. یک سازمان می‌تواند چند شعبه داشته باشد. هیچ داده‌ای بین مشتریان مشترک نیست.

**مشتری اول: سوپرمارکت.** اولویت‌ها: سرعت صندوق، تعداد بالای کالا (ده‌ها هزار SKU)، کالای وزنی، تخفیف و پروموشن، چاپ فیش، شیفت صندوق‌دار، شمارش و کسری موجودی، کالای تاریخ‌دار.

منطق اختصاصی سوپرمارکت نباید در هسته قفل شود؛ از طریق پیکربندی و قواعد اعمال شود.

**خارج از دامنه‌ی نسخه ۱:** سامانه مؤدیان (نسخه بعد؛ مدل داده آماده است)، حقوق و دستمزد (انتهای نقشه راه)، باشگاه مشتریان، انتقال داده از نرم‌افزار قبلی، هوش مصنوعی.

**مشخصات پایلوت:** ۳ تا ۷ صندوق، حداقل ۱۰۰۰ فاکتور در روز، کارت‌خوان بانک ملت، پرینتر فیش USB، نمایش تومان، سال مالی از ۱ فروردین. جزئیات: [`open-questions.md`](open-questions.md).

## ۳. فناوری‌های قطعی

### ۳.۱. Backend
- Python (نسخه پایدار پشتیبانی‌شده؛ فعلاً 3.12+)، Flask با Application Factory و Blueprint برای هر ماژول.
- SQLAlchemy 2.x، Alembic برای Migration، Pydantic v2 برای اعتبارسنجی ورودی/خروجی، OpenAPI برای مستندات API.
- تنظیمات فقط از Environment Variable (پیشوند `NEXTCAM_`)؛ Logging ساختاریافته (JSON در production)؛ مدیریت متمرکز خطا.
- آزمون واحد، یکپارچه‌سازی و امنیت؛ **آزمون‌های دیتابیسی روی SQL Server واقعی**، نه SQLite.
- معماری **Modular Monolith**. بدون دلیل واقعی سراغ Microservices نرو.

لایه‌ها با مرز روشن: API/کنترلر ← اعتبارسنجی (schema) ← سرویس کسب‌وکار ← قواعد حسابداری و موجودی ← دسترسی به داده (repository) ← مدل و Migration. به‌صورت متقاطع: احراز هویت و مجوز، ممیزی، ارتباط با تجهیزات، همگام‌سازی.

کنترلر محل منطق حسابداری نیست. هر عملیات کسب‌وکار در **یک Unit of Work (یک تراکنش)** اجرا می‌شود.

### ۳.۲. پایگاه داده
- **اصلی: Microsoft SQL Server 2019 Standard** (نصب‌شده روی سیستم محلی؛ حداقل نسخه پشتیبانی‌شده 2019). برای توسعه/تست: SQL Server Developer یا Docker؛ CI: کانتینر رسمی SQL Server.
- SQLite **فقط** برای صف عملیات و داده‌ی ضروری آفلاین در Agent/کلاینت؛ هرگز جایگزین دیتابیس مرکزی برای کلاینت‌های شبکه.
- کلید اصلی: `UNIQUEIDENTIFIER` (UUID قابل تولید در کلاینت). کلید خارجی، Constraint و Index براساس الگوی واقعی جست‌وجو.
- مبالغ: `DECIMAL(19,4)`؛ مقدار کالا: `DECIMAL(19,3)` (کالای وزنی). **هرگز Float.**
- زمان‌ها: `DATETIMEOFFSET`/UTC در دیتابیس؛ تاریخ شمسی فقط در لایه نمایش و ورودی.
- همزمانی خوش‌بینانه با `rowversion`.
- Query پارامتری؛ جلوگیری از N+1؛ صفحه‌بندی؛ سیاست نگهداری و آرشیو؛ `created_at`/`updated_at`/`created_by`.
- تفکیک شناسه داخلی (UUID) از شماره نمایشی سند.
- نام‌گذاری قطعی Constraintها (naming convention) برای Migration پایدار.

### ۳.۳. Frontend
React، TypeScript، Vite، Tailwind CSS، shadcn/ui، TanStack Query، React Hook Form، Zod، کتابخانه نمودار.
فارسی و RTL واقعی، واکنش‌گرا، مناسب کار طولانی‌مدت. **رابط کاربری هرگز مستقیم به دیتابیس وصل نمی‌شود**؛ فقط از طریق API.
صفحه صندوق (POS) باید کاملاً با صفحه‌کلید و بارکدخوان کار کند و برای صفحه‌نمایش لمسی هم مناسب باشد.

### ۳.۴. اندروید
Flutter/Dart برای ویزیتور: ورود امن، مشتریان مجاز، سفارش و پیش‌فاکتور، قیمت و موجودی مجاز، صف آفلاین پایدار، همگام‌سازی، جلوگیری از سفارش تکراری (Idempotency-Key)، مدیریت انقضای نشست، نگهداری امن توکن. **اتصال مستقیم به SQL Server ممنوع.**

## ۴. معماری اجرا

۱. **شبکه داخلی (حالت پیش‌فرض سوپرمارکت):** Backend و SQL Server روی سرور/سیستم فروشگاه؛ صندوق‌ها از مرورگر به API؛ تجهیزات محلی از طریق Device Agent روی هر صندوق.
۲. **سرور مرکزی:** Backend روی سرور (امکان میزبانی در ایران)، ارتباط امن با شعب، داشبورد چندشعبه، پشتیبان و بازیابی آزمایش‌شده.
۳. **ترکیبی:** عملیات محلی در شعبه، صف پایدار، همگام‌سازی کنترل‌شده با مرکز، یکپارچگی اسناد مالی.

وجود رابط وب به معنی کارکرد آفلاین نیست؛ آفلاین یعنی ذخیره محلی، صف پایدار، قواعد تعارض، مجوز محلی و همگام‌سازی پیاده‌سازی‌شده و آزمایش‌شده.

## ۵. ماژول‌ها

> برای هر ماژول، «تعریف تکمیل» در §۱۹ اعمال می‌شود. ترتیب ساخت در ROADMAP است.

**۱. حسابداری مالی** — کدینگ سطوح قابل تنظیم (گروه، کل، معین، تفصیلی)؛ سند دستی با مجوز؛ سند خودکار از فروش/خرید/دریافت/پرداخت از طریق **Posting Rules**؛ دفتر روزنامه، کل، معین؛ تراز آزمایشی؛ سود و زیان؛ ترازنامه؛ گردش و مانده حساب؛ دوره مالی (سال مالی شمسی قابل تنظیم)؛ **سند افتتاحیه و اختتامیه خودکار**؛ بستن دوره؛ وضعیت موقت/قطعی؛ برگشت و اصلاح با سابقه؛ مرکز هزینه (اختیاری)؛ پیوند سند عملیاتی ↔ سند حسابداری؛ رد سند نامتوازن؛ تاریخچه تغییرات.

**۲. فروش و صندوق** — کالا و خدمت؛ فاکتور، پیش‌فاکتور، برگشت؛ تخفیف ردیفی و کلی؛ **لیست قیمت چندگانه** (خرده، عمده، همکار)؛ **پروموشن زمان‌دار** (درصدی، مبلغی، n+1)؛ مالیات و عوارض قابل پیکربندی؛ پرداخت نقدی، کارت‌خوان، ترکیبی، نسیه با سقف اعتبار؛ چاپ فیش حرارتی و فاکتور A4/A5؛ **شیفت صندوق‌دار** (باز کردن با موجودی اولیه، بستن با شمارش وجه و ثبت کسری/اضافه)؛ **تعلیق فاکتور** (hold/recall)؛ کنترل دسترسی به تخفیف، ابطال و برگشت؛ ممیزی رویدادهای حساس؛ **فیلدهای رزرو مؤدیان** (شناسه مالیاتی کالا، شماره منحصربه‌فرد مالیاتی، وضعیت ارسال).
قواعد مالیاتی براساس مقررات جاری؛ بدون ادعای تأیید قانونی یا اتصال رسمی بدون مستند و آزمون.

**۳. انبارداری** — چند انبار؛ کالا، گروه، ویژگی؛ کد کالا، **چند بارکد برای هر کالا**، **بارکد ترازو** (EAN-13 با وزن یا قیمت؛ الگوی پیشوند قابل تنظیم)؛ چند واحد و تبدیل؛ رسید، حواله، انتقال؛ اصلاح موجودی با مجوز؛ شمارش و مغایرت؛ کاردکس؛ حداقل/حداکثر و هشدار؛ **قیمت تمام‌شده میانگین موزون متحرک** (FIFO بعداً)؛ سیاست موجودی منفی؛ بچ/سریال/انقضا (اختیاری، برای سوپرمارکت: انقضا)؛ ارزش موجودی؛ کم‌گردش و راکد؛ **چاپ لیبل قیمت و بارکد**.
موجودی فقط از گردش‌های معتبر انبار تغییر می‌کند؛ نه با تغییر یک فیلد عددی.

**۴. خرید و تأمین‌کنندگان** — تأمین‌کننده؛ درخواست و سفارش خرید؛ رسید کالا؛ فاکتور و برگشت خرید؛ هزینه‌های جانبی (سرشکن در بهای تمام‌شده)؛ پرداخت؛ مانده و گردش؛ مقایسه قیمت خرید؛ پیوند با انبار و حسابداری.

**۵. خزانه‌داری** — صندوق نقدی، حساب بانکی؛ دریافت، پرداخت، انتقال؛ چک دریافتی و پرداختی و وضعیت آن؛ سررسیدها؛ مغایرت‌گیری بانکی؛ پیوند تراکنش کارت‌خوان با دریافت؛ شناسه پیگیری بانکی؛ صف تطبیق تراکنش‌های نامشخص.

**۶. طرف‌حساب‌ها** — حقیقی و حقوقی؛ مشتری، تأمین‌کننده، هر دو؛ تماس، نشانی، شناسه‌ها (کد ملی، شناسه ملی، کد اقتصادی)؛ سقف اعتبار؛ مانده و گردش؛ سوابق؛ یادداشت و پیگیری؛ گروه‌بندی؛ کنترل دسترسی به اطلاعات حساس.

**۷. ویزیتور و توزیع** — ویزیتور؛ تخصیص مشتری؛ برنامه بازدید؛ سفارش آنلاین/آفلاین؛ همگام‌سازی؛ کنترل تکرار؛ وضعیت سفارش و تحویل؛ گزارش عملکرد.

**۸. کاربران و مجوزها** — کاربر، نقش، مجوز جزئی (`module.resource.action`)؛ محدوده شعبه/انبار/صندوق؛ نشست و خروج؛ سیاست رمز؛ قفل پس از تلاش ناموفق؛ MFA اختیاری؛ ثبت عملیات حساس؛ تفکیک مشاهده، ایجاد، ویرایش، تأیید، ابطال، گزارش. **اجرای مجوز فقط در Backend.**

**۹. گزارش‌ساز و داشبورد** — فروش، سود و زیان، موجودی، گردش کالا، بدهکاران، بستانکاران، دریافت و پرداخت، شعب، کاربران، صندوق و کارت‌خوان، تراکنش نامشخص، آفلاین و همگام‌سازی، سخت‌افزار؛ فیلتر ترکیبی؛ Excel و PDF؛ فیلتر ذخیره‌شده؛ کنترل دسترسی؛ صفحه‌بندی. گزارش مالی فقط از اسناد قطعی.

**۱۰. امنیت و پشتیبان‌گیری** — §۹ و §۱۳.

**۱۱. شعب** — شعبه، کاربران، انبارها، صندوق‌ها و سیاست‌های هر شعبه؛ شماره‌گذاری اسناد (ADR-0005)؛ گزارش تجمیعی؛ کنترل دسترسی بین شعب؛ همگام‌سازی و تعارض؛ جلوگیری از ثبت تکراری.

**۱۲. ورود و خروج اطلاعات** — ورود کالا، بارکد، طرف‌حساب و مانده‌های افتتاحیه از Excel با پیش‌نمایش، اعتبارسنجی ردیف‌به‌ردیف و گزارش خطا؛ هیچ ورودی‌ای بدون تأیید کاربر ثبت نمی‌شود.

**۱۳. حقوق و دستمزد (انتهای نقشه راه)** — کارکنان، اقلام و کسورات، دوره، محاسبه قابل تنظیم، سند حسابداری، دسترسی محدود و محرمانگی. قواعد قانونی باید براساس مقررات جاری بررسی شوند.

**۱۴. سامانه مؤدیان (نسخه بعد)** — ارسال صورتحساب الکترونیکی، صف ارسال مجدد، وضعیت‌ها، ابطال و اصلاحیه؛ فقط براساس مستندات رسمی و محیط آزمون رسمی.

**نمایش مبالغ:** ذخیره همیشه به ریال؛ نمایش ریال یا تومان قابل تنظیم برای هر سازمان.

اتصال سخت‌افزار از لایه مستقل. پشتیبانی هر دستگاه باید به‌صورت مستقل اثبات و در رجیستری سازگاری ثبت شود.

### ۶.۲. Device Agent (Python، سرویس ویندوز)
نصب و اجرای کنترل‌شده؛ API محلی محدود فقط روی `127.0.0.1`؛ احراز هویت محلی (توکن جفت‌سازی با Backend)؛ بررسی Origin؛ محافظت در برابر DNS rebinding (بررسی Host)؛ مدیریت وضعیت دستگاه، timeout، قفل عملیات هم‌زمان، لاگ، نسخه کانکتور، بازیابی پس از راه‌اندازی مجدد. **هیچ API برای اجرای فرمان دلخواه یا SQL.**
محدودیت Chrome در دسترسی صفحه HTTPS به localhost (Private/Local Network Access) باید در فاز ۰ با نمونه اولیه آزمایش شود. کنترل‌های امنیتی برای رفع خطای اتصال غیرفعال نمی‌شوند.

### ۶.۳. بارکدخوان USB HID
Keyboard Wedge: دریافت در فیلد فوکوس‌شده؛ تشخیص اسکن از تایپ با زمان‌بندی کاراکترها؛ پسوند Enter/Tab قابل تنظیم؛ کنترل بارکد ناقص/نامعتبر؛ جلوگیری از submit ناخواسته؛ اسکن متوالی؛ ورود دستی؛ خطای کالای ناشناخته؛ **آزمون چیدمان صفحه‌کلید فارسی** (اسکنر روی کیبورد فارسی کاراکتر اشتباه می‌فرستد — نگاشت معکوس لازم است).
HID Keyboard ≠ HID POS ≠ Virtual COM. دریافت سراسری در پس‌زمینه ویندوز جداگانه طراحی و آزمایش شود.

### ۶.۴. کارت‌خوان بانکی LAN
مدل و PSP هنوز مشخص نیست؛ هیچ مدل، SDK، پروتکل یا پورت سازگار فرض نشود.
اجزا: `PaymentTerminalService`، `PaymentTerminalAdapter`، `PaymentTerminalAdapterFactory`، `TerminalConnectionManager`، `PaymentReconciliationService`، `PaymentAuditService`، `MockPaymentTerminalAdapter`. قرارداد در [`docs/hardware/payment-terminal-adapter.md`](hardware/payment-terminal-adapter.md).
عملیات: وضعیت دستگاه، شروع پرداخت، استعلام، نتیجه، لغو/ابطال و استرداد (فقط در صورت پشتیبانی رسمی).
پیش از تأیید هر مدل: برند و مدل، PSP، Firmware، نوع اتصال، پروتکل ECR/SDK رسمی، روش ارسال مبلغ و دریافت نتیجه و استعلام، کدهای خطا و رفتار timeout، پیش‌نیازهای ویندوز، مجوز SDK، محیط آزمون.
پورت LAN اثبات سازگاری نیست. SDK اندرویدی معادل پروتکل LAN نیست. مهندسی معکوس پروتکل بانکی و ساخت پاسخ موفق جعلی ممنوع.

**وضعیت‌ها:** `Created`، `Pending`، `Approved`، `Declined`، `Unknown`، `ReconciliationRequired`، `Cancelled` — مستقل از وضعیت فاکتور و سند.
قواعد: ارسال ≠ موفقیت؛ timeout ≠ شکست؛ تراکنش نامشخص بدون استعلام دوباره پرداخت نمی‌شود؛ نتیجه باید به همان درخواست و فاکتور مربوط باشد؛ پرداخت و سند تکراری ممنوع؛ اگر استعلام ممکن نیست ← `ReconciliationRequired`؛ PAN کامل، Track، CVV و PIN هرگز ذخیره یا لاگ نمی‌شوند؛ نتیجه شبیه‌ساز هرگز پرداخت واقعی نیست.
شبکه: IP ثابت یا DHCP Reservation؛ فقط پورت‌های مستند؛ عدم دسترسی اینترنتی کارت‌خوان؛ هر صندوق ← کارت‌خوان مجاز مشخص؛ مدیریت تراکنش هم‌زمان؛ تغییر تنظیمات فقط برای کاربر مجاز.

### ۶.۵. رجیستری سازگاری
برای هر دستگاه: برند، مدل، Firmware، اتصال، SDK/درایور، سیستم‌عامل، قابلیت‌های تأییدشده، نسخه کانکتور، تاریخ و شواهد آزمون، محدودیت‌ها، وضعیت (`Verified`، `Conditionally Supported`، `Not Verified`، `Unsupported`). کارت‌خوان تا آزمون واقعی `Not Verified`.

### ۶.۶. شبیه‌ساز
سناریوها: موفق، رد، timeout، نامعلوم، قطع ارتباط، تأخیر، درخواست تکراری، استعلام، نیاز به تطبیق. **فقط در محیط development/test** (`NEXTCAM_ENABLE_MOCK_PAYMENT_TERMINAL`؛ در production در زمان بارگذاری تنظیمات رد می‌شود).

## ۷. یکپارچگی حسابداری و انبار
- سند قطعی متوازن است (Σبدهکار = Σبستانکار) و در دیتابیس هم کنترل می‌شود.
- اسناد خودکار از **Posting Rules** تولید می‌شوند: برای هر نوع رویداد (فروش، برگشت فروش، خرید، دریافت، پرداخت، تعدیل موجودی، کسری صندوق) نگاشت قابل تنظیم به حساب‌ها.
- موجودی فقط از طریق گردش‌های انبار تغییر می‌کند؛ هر گردش بهای تمام‌شده را ثبت می‌کند.
- برگشت فروش و خرید به سند اصلی پیوند دارند.
- عملیات چندمرحله‌ای در یک تراکنش دیتابیس؛ درخواست تکراری با همان Idempotency-Key نتیجه‌ی قبلی را برمی‌گرداند.
- حذف فیزیکی سند قطعی ممنوع؛ فقط سند برگشت/اصلاحی با سابقه.
- شماره اسناد طبق ADR-0005.
- Float برای مبلغ ممنوع.
- تاریخ استاندارد در Backend؛ تقویم شمسی در نمایش.

## ۸. آفلاین و همگام‌سازی
صف پایدار محلی؛ شناسه یکتای هر عملیات (UUID + Idempotency-Key)؛ زمان محلی و زمان دریافت سرور؛ شعبه، دستگاه و کاربر؛ وضعیت، تعداد تلاش و خطا؛ جلوگیری از اجرای دوباره؛ مدیریت تعارض؛ سابقه؛ ادامه پس از خاموشی؛ مجوز محلی؛ گزارش ناموفق‌ها.
تعارض مالی و موجودی **هرگز** با Last-Write-Wins حل نمی‌شود. قطع اینترنت در تراکنش بانکی نه موفقیت است نه شکست. پروتکل در [`docs/sync/protocol.md`](sync/protocol.md).

## ۹. امنیت
احراز هویت امن (ADR-0004)؛ RBAC با مجوز جزئی و محدوده شعبه/انبار؛ اعتبارسنجی همه ورودی‌ها؛ Query پارامتری؛ XSS و CSRF متناسب با مدل؛ Rate limit روی ورود و نقاط حساس؛ انقضای نشست و توکن؛ اسرار فقط در Environment/Secret store؛ TLS؛ ممیزی رویدادهای حساس؛ عدم ثبت اطلاعات محرمانه در لاگ؛ پیام خطای عمومی بدون جزئیات داخلی (شناسه رخداد برای پیگیری)؛ کنترل دسترسی به پشتیبان؛ اسکن وابستگی‌ها در CI؛ بررسی امنیت API محلی Agent.
هیچ عملیات مالی یا مدیریتی فقط با مخفی‌کردن دکمه محافظت نمی‌شود.

## ۱۰. UI/UX
فارسی و RTL واقعی؛ فونت فارسی خوانا (مثل وزیرمتن)؛ ارقام فارسی در نمایش، پذیرش ارقام فارسی و لاتین در ورودی؛ داشبورد؛ منوی ماژولار؛ جست‌وجوی سریع (Ctrl+K)؛ فرم و جدول قابل استفاده با صفحه‌کلید؛ صفحه‌بندی؛ فیلتر ترکیبی؛ نمایش واضح خطا؛ Loading و Empty State؛ تأیید عملیات حساس؛ وضعیت ذخیره و همگام‌سازی؛ وضعیت تجهیزات و کارت‌خوان (متصل، قطع، آماده پرداخت، در حال پرداخت، موفق، ناموفق، نیازمند بررسی) با **متن + آیکون + رنگ**؛ مناسب نمایشگر فروشگاهی و لمسی؛ کنتراست و دسترس‌پذیری؛ تقویم شمسی؛ مؤلفه‌های یکپارچه.
**صفحه صندوق:** کلیدهای میانبر (F-keys) برای پرداخت، تعلیق، حذف ردیف، تغییر مقدار؛ هدف: ثبت ردیف با اسکن بدون نیاز به ماوس.

## ۱۱. کارایی
Query پرتکرار بهینه؛ Index براساس تحلیل؛ گزارش حجیم صفحه‌بندی و در صورت نیاز صف پردازش؛ تراکنش مالی جدا از پردازش‌های غیرضروری؛ timeout مشخص برای تجهیزات؛ خطای شبکه رابط فروش را متوقف نکند؛ Cache فقط با سیاست معتبر و نه برای مانده‌های مالی حساس؛ آزمون با داده واقع‌بینانه (مثلاً ۵۰ هزار کالا، ۳۰۰۰ فاکتور روزانه). هیچ عدد ظرفیت یا سرعتی بدون آزمون بار تضمین نمی‌شود.

## ۱۲. گزارش‌ها
همان فهرست ماژول ۹ + گزارش شیفت صندوق، کسری/اضافه صندوق، پروموشن‌ها، کالاهای نزدیک به انقضا. دسترسی براساس نقش.

## ۱۳. پشتیبان‌گیری و بازیابی
Backup بومی SQL Server (Full + Differential + Log با Recovery Model مناسب)؛ زمان‌بندی با SQL Server Agent (موجود در Standard)؛ `CHECKSUM` و `RESTORE VERIFYONLY`؛ نسخه محلی + مقصد جداگانه؛ رمزنگاری Backup؛ محدودسازی دسترسی؛ ثبت نتیجه و هشدار شکست؛ سیاست نگهداری؛ **آزمون دوره‌ای Restore روی دیتابیس جدا**؛ مستند بازیابی کامل. ایجاد فایل پشتیبان به‌تنهایی موفقیت نیست.

## ۱۴. هوش مصنوعی (آینده)
پیش‌بینی فروش، پیشنهاد سفارش خرید، کم‌گردش‌ها، هشدار مغایرت، تحلیل نقدینگی، دستیار گزارش. هسته مالی به هوش مصنوعی وابسته نیست؛ هیچ مدل بدون مجوز و تأیید انسانی سند قطعی یا تغییر موجودی ایجاد نمی‌کند.

## ۱۵. تست
Backend: سرویس، API، مجوز، Migration (upgrade/downgrade روی SQL Server)، تراکنش مالی، Idempotency، اعتبارسنجی، خطا.
مالی: توازن، فروش و سند، برگشت، دریافت و پرداخت، ترکیبی، عدم تکرار، تعارض آفلاین، تطبیق نامشخص، میانگین موزون.
سخت‌افزار: اسکن متوالی، چیدمان فارسی، قطع USB، تغییر فوکوس، خطای Agent، قطع LAN، نتایج کارت‌خوان، timeout، استعلام، عدم تکرار، چاپ فیش، **آزمون با دستگاه واقعی**.
امنیت: دسترسی غیرمجاز، بین شعب، سوءاستفاده از API محلی، ورودی نامعتبر، افشای اطلاعات، نشست.
هیچ تستی موفق اعلام نمی‌شود مگر واقعاً اجرا شده باشد. تست شبیه‌ساز جایگزین تست سخت‌افزار واقعی نیست. برنامه کامل: [`docs/testing/test-plan.md`](testing/test-plan.md).

## ۱۸. قواعد همکاری
۱. قبل از تغییر، وضعیت واقعی پروژه را بررسی کن. ۲. بخش سالم را بی‌دلیل بازنویسی نکن. ۳. اطلاعات ناقص را صریح اعلام کن. ۴. درباره سخت‌افزار، پروتکل یا SDK اطلاعات ساختگی نساز. ۵. مدیریت خطا و اعتبارسنجی. ۶. منطق حسابداری در UI ممنوع. ۷. اتصال مستقیم کلاینت به دیتابیس ممنوع. ۸. حذف یا اصلاح بی‌سابقه سند قطعی ممنوع. ۹. آفلاین واقعاً پیاده و آزمایش شود. ۱۰. API امنیتی ضعیف برای ساده‌کردن سخت‌افزار ممنوع. ۱۱. پایان هر فاز: گزارش تغییرات، فایل‌ها، تست‌های اجراشده و نتایج، محدودیت‌ها. ۱۲. وضعیت واقعی هر قابلیت ناتمام. ۱۳. کد نمایشی به‌عنوان قابلیت عملیاتی ممنوع. ۱۴. هر تصمیم معماری مهم ← یک ADR. ۱۵. هر تغییر از طریق شاخه و Pull Request با CI سبز.

## ۱۹. تعریف تکمیل
ماژول تکمیل است وقتی: منطق کسب‌وکار پیاده شده، API و مجوزها کار می‌کنند، داده در SQL Server ذخیره می‌شود، خطاها مدیریت می‌شوند، تست‌ها اجرا و موفق شده‌اند، مستندات به‌روز است، ارتباط با ماژول‌های دیگر آزمایش شده و محدودیت‌ها مستند است.
کارت‌خوان تکمیل است وقتی مدل واقعی، پروتکل رسمی، ویندوز و سناریوهای موفق/ناموفق/نامشخص عملاً آزمایش شده باشند. بارکدخوان باید در گردش واقعی فروش و انبار آزمایش شود. Interface، Mock یا تست واحد به معنی آمادگی سخت‌افزار نیست.
