# آزمون بار با حجم داده‌ی واقع‌بینانه (فاز ۱۰)

**تاریخ:** ۱۴۰۵/۰۷/۲۸ · **محیط:** محیط توسعه، ۴ هسته‌ی مشترک بین برنامه و SQL Server 2019 (Docker)، ۱۵GB حافظه. سرور واقعی فروشگاه این اعداد را تأیید نکرده است.

## داده
ساخته‌شده با `backend/scripts/volume_data.py`:
- **از مسیر واقعی:** همه‌چیز از API و سرویس‌های واقعی ساخته شد (همان قیمت‌گذاری، بهای میانگین، سند حسابداری، شماره‌گذاری و triggerها). فقط ساعت شبیه‌سازی شد.
- **دوره:** ۶۱ روز (۱۴۰۵/۰۳/۳۱ تا ۱۴۰۵/۰۵/۳۰)، حدود ۱۰۰۰ فاکتور در روز در ۷ صندوق.

**الگوی فروش:**
- **ساعت‌ها:** پیک ظهر و عصر، و جمعه‌ها شلوغ‌تر.
- **سبد:** ۱ تا ۱۵ قلم.
- **کالا:** پرفروش‌ها به‌صورت Zipf.
- **پرداخت:** ۵۵٪ کارت، ۴۲٪ نقد، ۳٪ نسیه.
- **دیگر رویدادها:** ۱٪ برگشت؛ خرید هفتگی از ۴۰ تأمین‌کننده؛ دریافت هفتگی از مشتریان نسیه.

**مقیاس به‌دست‌آمده:**

| جدول | ردیف |
|---|---|
| کالا | ۱۲٬۰۰۰ |
| مشتری | ۱٬۵۰۰ |
| فاکتور فروش | ۶۳٬۹۱۶ |
| ردیف فاکتور | ۳۵۱٬۴۵۵ |
| گردش انبار | ۴۲۰٬۶۹۹ |
| سند حسابداری | ۶۷٬۳۹۵ |
| ردیف سند | ۳۲۲٬۱۸۵ |
| فاکتور خرید | ۳۲۰ |
| حجم فایل داده | حدود ۱٫۹GB |

- **خطا:** فقط ۲ مورد در ۶۲٬۰۰۰ فروش، هر دو تلاش مولد برای برگشت ردیفی که قبلاً برگشت خورده بود. سرور به‌درستی رد کرد.
- **بررسی سلامت:** پس از تولید داده، `check-integrity` همه را ok گزارش کرد. هر سند تراز و موجودی برابر گردش بود.

| ۷ صندوق با حداکثر سرعت (اشباع) | **۳٫۸۴** (حداکثر ۶) | ۴۹ / ۸۲ms | ۶۹ / ۱۱۶ms | ۱۱۴۴ / ۱۴۶۱ms | ۰ |

## ایرادهایی که این آزمون پیدا کرد (همه اصلاح شدند و تست بازگشت دارند)
1. **سقف ۲۱۰۰ پارامتر SQL Server:**
   - **علامت:** سند انبار بالای حدود ۲۱۰۰ ردیف خطای ۵۰۰ می‌داد؛ گزارش‌های فروش بر اساس کالا، گردش کالا و بدهکاران هم با بیش از ۲۱۰۰ کالا یا شخص.
   - **اصلاح:** بارگذاری تکه‌تکه (`load_by_ids` و `load_columns_by_ids`).
2. **کاردکس و فهرست اسناد انبار:** پس از اولین سند فروش یا خرید، خطای ۴۰۰ می‌دادند.
3. **فهرست فاکتورها:** ردیف‌ها، صندوق و کاربر هر فاکتور جداگانه خوانده می‌شد (N+1).
4. **کندی گزارش فروش و داشبورد:**
   - **علت:** ثابت‌های `'sale'`، `'return'` و ±۱ داخل CASEِ هر ردیف، به‌صورت پارامتر نوع‌دار فرستاده می‌شدند. همین پرس‌وجو در SQL خام ۱۳۵ms و از برنامه ۲٫۹s طول می‌کشید.
   - **اصلاح:** ثابت‌ها حالا در متن SQL نوشته می‌شوند. این‌ها ثابت کد هستند، نه ورودی کاربر.
   - **نام کالاها:** به‌جای شیء کامل (با همه‌ی بارکدها و واحدها)، فقط ستون‌های لازم خوانده می‌شوند.

## محدودیت‌ها
- **محیط:** اعداد روی محیط مشترک توسعه است. روی سرور فروشگاه با `load_test.py` تکرار شود (چک‌لیست تحویل).
- **حجم:** دو ماه داده است. مولد قابل ادامه است (`--resume`) و یک سال کامل اجرا نشد. پیش‌بینی خطی برای یک سال: گزارش «کل دوره» تا حدود ۶ برابر کندتر. بازه‌ی گزارش هم حداکثر یک سال است.
- **خروجی Excel و snapshot صندوق** چند ثانیه طول می‌کشند:
  - Excel دستی و گاه‌به‌گاه است.
  - Agent داده‌ی آفلاین را با ETag می‌گیرد و فقط با تغییر داده دوباره دانلود می‌کند.

  هر دو قابل‌قبول ارزیابی شدند و بهینه نشدند.
- **کارت‌خوان و چاپگر** در این آزمون نبودند. پرداخت کارتی با شماره‌ی پیگیری دستی است.
